# MVPから実運用への差分洗い出し r1

- 作成日: 2026-08-29 15:40頃
- 位置づけ: 分析・記録のみ。実装コードは変更していない
- 前提: `hackathon-contract.md`の「Later / explicitly cut」（ログイン、汎用プロフィール、複数ペルソナ、多機能ダッシュボード）と「Change boundaries」（production未承認）により、以下の差分は今回のP0スコープでは意図的に省かれたもの。バグではなく設計上の境界線
- 目的: 本人から指摘のあった「secret codeでのデモがつまらない」「イベント場所入力などが実用と違う」を起点に、実運用へ進める際に埋めるべき差分を洗い出す。今回のハッカソン内での実装は行わない

## 1. 認証・オンボーディングモデル

| 項目 | 現状(MVP) | 実運用に必要なもの |
|---|---|---|
| 管理者ログイン | 単一の`DEMO_ADMIN_SECRET`をパスワード欄に手入力（`main.ts:72-99`, `worker.ts:90-104`） | 誘い手ごとのアカウント/OAuthログイン、secret共有の廃止 |
| 誘い手の識別 | セッションのみ、実名・連絡先を保存しない設計 | 実運用では誘い手の本人確認（大学メール等の軽量認証）が必要になりうる |
| デモ体験の入り口 | `/admin`から手動でsecretを入れて開始 | 実運用では「イベントを作る」ボタンから直接開始でき、secret入力という工程自体が不要 |

## 2. イベント作成・場所入力

| 項目 | 現状(MVP) | 実運用に必要なもの |
|---|---|---|
| イベント内容 | `worker.ts:136-143`で固定文字列（イベント名・日時・待合せ時刻・場所・合図すべてハードコード） | 誘い手がイベント名・日時・待合せ場所・合図を入力するフォーム |
| 場所の入力方法 | テキストラベルのみ、地図やジオコーディングなし | 住所検索・地図ピン選択・現在地からの候補表示など、実際の場所入力UI |
| 同時に開けるイベント数 | `demo_key='seed-demo'`固定、`one_live_demo`ユニーク制約により**常に1件だけ** | 誘い手ごと・イベントごとに複数のinviteを同時に発行できる設計（invite管理の一覧画面も必要） |
| イベントの永続性 | resetのたびに前のイベントが失効し、新しいデモイベントに置き換わる | 実イベントは誘い手が能動的に終了させるまで有効であるべき（現状のreset＝作り直し、という設計とは異なる） |

## 3. 参加者体験

| 項目 | 現状(MVP) | 実運用に必要なもの |
|---|---|---|
| 招待の受け取り方 | 対面QR/fallback URLのみ | チャットやメールでの招待リンク共有（対面前提を外す場合） |
| 支援範囲の選択肢 | `entrance/reception/first10/decline`の4択固定 | イベント種別に応じて選択肢自体をカスタマイズできる余地 |
| 通知 | なし（誘い手・参加者ともpollingで手動確認） | 承認・確定時のpush通知やメール通知 |

## 4. 運用・信頼性

| 項目 | 現状(MVP) | 実運用に必要なもの |
|---|---|---|
| 匿名イベント作成の乱用対策 | 非目標として明示的に除外（`mvp-design-canvas-r4.md` Non-goals） | 主催者確認、審査、通報・ブロック機能 |
| 到着・合流の共有 | 非目標（P1として完全に削除済み、`mvp-design-canvas-r5.md` Scope freeze） | 「着いた」「会えた」の共有、位置情報連携 |
| rate limit・セッションTTL | デモ利用規模（同時数名）を前提にした値 | 実際の同時アクセス数に応じた見直し、DDoS対策 |
| 監視・運用ツール | health checkのみ | ダッシュボード、アラート、ログ集約 |
| production環境 | 未作成・未承認（stagingのみ） | production D1/Worker、独自ドメイン、Secretローテーション運用 |

## 5. 法務・プライバシー

- 現状は実名・顔画像・大学名・現在地・連絡先を一切保存しない設計（意図的な安全側の制約）。実運用で本人確認や通知を導入する場合、個人情報の取り扱い方針（利用規約・プライバシーポリシー）が新たに必要になる。
- 実在の場所・実在の人物を扱うため、誤情報や無断使用への対応方針（削除依頼の窓口等）が必要になる。

## 優先度についての所見（今回は実装しない、方向性のメモ）

実運用へ進める場合、最初に効くのは次の3つだと考えられる。

1. **イベント作成フォーム**（場所・日時・合図を誘い手が入力）— 固定デモイベントの卒業
2. **secret共有をやめた誘い手ログイン**（簡易でよい。例: 誘い手ごとのマジックリンク）
3. **複数invite同時発行**（`one_live_demo`制約の設計見直し）

いずれも今回の120分MVPの承認範囲外であり、今回のハッカソン内では着手しない。
